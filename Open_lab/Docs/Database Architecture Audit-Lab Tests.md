# خطة المهمة: تدقيق معماري لقاعدة بيانات أنواع التحاليل — المرحلة الثانية

## Context (السياق)

نظام **Open_lab** هو نظام WPF/.NET 8 لإدارة معامل التحاليل الطبية باستخدام Entity Framework Core 8 و SQL Server. أنواع التحاليل تنقسم إلى:
- **بسيطة** (Single-Component): مكوّن واحد فقط ينتج قيمة واحدة (مثل Uric Acid)
- **مركّبة** (Multi-Component / Profiles): تتكوّن من 20+ مكوّن فرعي، كل مكوّن له وحدة قياس ومعدلات طبيعية مستقلة (مثل CBC)

كل مكوّن يحتاج لمعدلات طبيعية متعددة تختلف بـ:
- **جنس المريض** (ذكر/أنثى)
- **الفئة العمرية** (رضيع، طفل، مراهق، بالغ، كبير في السن)

المهمة هي **تدقيق التصميم الحالي للقاعدة** للتأكد من قدرته على دعم هذه المتطلبات، وإنتاج تقرير Markdown شامل بمخرج وحيد:

**`Database Architecture Audit - Lab Tests.md`**

**هذه مهمة تحليلية بحتة — لن يتم تعديل أي كود أو ملف باستثناء التقرير الناتج.**

## الفجوات المعمارية المكتشفة (ملخّص)

### 🔴 الفجوة #1 (الأكثر حرجاً) — المعدلات الطبيعية لا ترتبط بالمكوّن الفرعي
- **الموقع**: `Entities.cs:231-243`، `OpenLabDbContext.cs:222-230`، `InitialCreate.cs:445-468`
- **المشكلة**: جدول `TestReferenceRanges` يحتوي على `TestId` فقط، **لا يوجد عمود `ParameterId`**.
- **الدليل القاطع**: في `ResultsService.cs:280-285`، دالة `ValidateResultAsync` تبحث:
  ```csharp
  await _db.TestReferenceRanges
      .Where(r => r.TestId == testId)
      .Where(r => r.Gender == null || r.Gender == gender)
      .Where(r => (r.AgeFrom == null || age >= r.AgeFrom) && ...)
  ```
  المقارنة تتم بـ `testId` فقط، بدون فلترة بـ `ParameterId`.
- **الأثر**: تحليل CBC الذي يحتوي على 14 مكوّن فرعي (Hemoglobin, WBC, RBC, Platelets...) سيخزّن معدلاته الطبيعية على مستوى التحليل ككل. **لا يمكن تخزين معدلات مختلفة لكل مكوّن**.

### 🔴 الفجوة #2 — التعليقات لا ترتبط بالمكوّن الفرعي
- **الموقع**: `Entities.cs:245-263`، `TestComments` table
- **المشكلة**: نفس المشكلة — `TestComments.TestId` فقط، بدون `ParameterId`.
- **الأثر**: لا يمكن تخصيص تعليق "High Hemoglobin" مختلف عن "Low WBC" في نفس التحليل.

### 🟡 الفجوة #3 — ازدواجية في وحدة القياس
- **الموقع**: `Tests.UnitId` (Entities.cs:181) و `TestParameters.UnitId` (Entities.cs:290)
- **المشكلة**: التحاليل المركّبة لا تحتاج إلى `Test.UnitId` لأن كل مكوّن له وحدته. هذا الازدواج يخلق غموضاً عن "وحدة التحليل الكلية".
- **الأثر**: غير مدمّر، لكنه يربك تصميم البيانات ويستوجب قواعد عمل متعرّجة في الواجهة.

### 🟡 الفجوة #4 — لا يوجد جدول للفئات العمرية المرنة
- **الموقع**: `TestReferenceRanges` يستخدم `AgeFrom` و `AgeTo` كأرقام صحيحة (سنوات)
- **المشكلة**: لا يوجد جدول `AgeGroups` يسمح بتعريف فئات عمرية ذات اسم وحدود قابلة للتعديل. الفئات الحالية مضمّنة كأرقام مكررة في كل سجل.
- **الأثر**: تكرار البيانات، عدم وجود مصدر موثوق للفئات العمرية، صعوبة إضافة فئات جديدة دون تعديل كل السجلات. كذلك `int` لا يدعم الفترات بالأشهر (مهم للرضع 0-1 سنة).

### 🟡 الفجوة #5 — لا يوجد عمود `Description` لأنواع التحاليل
- **الموقع**: جدول `Tests` (Entities.cs:173-204)
- **المشكلة**: السياق طلب "وصف أو ملاحظات اختيارية لكل نوع تحليل" — لا يوجد عمود `Description` أو `Notes`.
- **الأثر**: لا يمكن تخزين ملاحظات إضافية عن التحليل (تعليمات التحضير، الاستطباب الطبي، إلخ).

### ✅ نقاط مدعومة بالكامل:
- ✅ تصنيف التحاليل في مجموعات (`TestGroup`)
- ✅ تخزين السعر (`Test.Price`، مع `CostPrice`/`PatientPrice` للتحاليل الخارجية)
- ✅ المكوّنات الفرعية المتعددة (`TestParameter` + Cascade Delete)
- ✅ التمييز بناءً على الجنس (`Gender`) ضمن المعدل
- ✅ تمييز نطاق عمري (`AgeFrom`/`AgeTo`)
- ✅ إضافة/تعديل/حذف من واجهة المستخدم عبر `TestCatalogService` + `TestCatalogViewModel`
- ✅ Indexes على Foreign Keys + Unique Index على `Tests.Code`
- ✅ Precision(18,2) لجميع المبالغ والمعدلات الرقمية

### 6. التصميم المقترح للإصلاح
**ملاحظة: للمراجعة فقط — لن يُنفّذ في هذه المرحلة.**

التعديلات المقترحة مرتّبة حسب الأولوية:

#### الأولوية 1 (حرجة) — إضافة `ParameterId` إلى `TestReferenceRanges`
```
TestReferenceRanges:
  + ParameterId (int, FK -> TestParameters, Nullable)
  (مع جعل المعدل مرتبطاً بالمكوّن مباشرةً)
```
في حالة التحاليل البسيطة: `ParameterId` يشير إلى المكوّن الوحيد. في حالة المركّبة: لكل مكوّن سجلاته المنفصلة.

#### الأولوية 2 (حرجة) — إضافة `ParameterId` إلى `TestComments`
```
TestComments:
  + ParameterId (int, FK -> TestParameters, Nullable)
```

#### الأولوية 3 (متوسطة) — جدول `AgeGroups` للفئات العمرية المرنة
```
AgeGroups (جدول جديد):
  - AgeGroupId (PK)
  - Name (string)             مثل "رضيع"، "بالغ"
  - AgeFromMonths (int)       لدعم الرضع
  - AgeToMonths (int)
  - DisplayOrder (int)

TestReferenceRanges:
  + AgeGroupId (int?, FK -> AgeGroups, Nullable)
  (مع الإبقاء على AgeFrom/AgeTo للتوافق)
```

#### الأولوية 4 (منخفضة) — إضافة `Description` إلى `Tests`
```
Tests:
  + Description (nvarchar(max), Nullable)
```

#### الأولوية 5 (تنظيم اختياري) — توضيح دور `Test.UnitId`
خياران:
- (أ) إبقاؤه فقط للتحاليل البسيطة وتجاهله للمركّبة (موثّق فقط).
- (ب) ضمان إنشاء `TestParameter` واحد افتراضي للتحاليل البسيطة، ونقل كل وحدات القياس إلى `TestParameter.UnitId`، ثم حذف `Test.UnitId` لاحقاً.

#### استراتيجية الترحيل (Migration Strategy)
- إضافة الأعمدة الجديدة كـ `Nullable` للحفاظ على البيانات الحالية.
- سكريبت ترحيل بيانات (Data Migration): لكل `TestReferenceRange` موجود مرتبط بتحليل بسيط، نسخ `ParameterId` من `TestParameter` الوحيد للتحليل.
- بعد التأكد، يمكن جعل `ParameterId` غير قابل لـ Null في Migration لاحقة.
